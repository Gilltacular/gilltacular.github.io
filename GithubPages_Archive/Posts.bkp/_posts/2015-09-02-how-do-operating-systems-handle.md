The definition of an interrupt is a signal that is sent from hardware devices or software to the processor when another computation or action needs attention. The interrupt, as the name implies, stops the currently executing code and responds to the need before continuing on to other instructions.

I feel the need for an interrupt is best described by a passage from the book Linux Device Drivers by Jessica McKeller, Alessandro Rubini, Jonathan Corbet, and Greg Kroah-Harman (2005) which describes this system with a defined clarity as shown in the following passage:
>"Although some devices can be controlled using nothing but their I/O regions, most real devices are a bit more complicated than that. Devices have to deal with the external world, which often includes things such as spinning disks, moving tape, wires to distant places, and so on. Much has to be done in a time frame that is different from, and far slower than, that of the processor. Since it is almost always undesirable to have the processor wait on external events, there must be a way for a device to let the processor know when something has happened. That way, of course, is interrupts."

According to the book Operating Systems Internals and Design Principles (Stallings, 2015), there are four main kinds of interrupts including:
>Program Interrupt - Generated by some condition that occurs as a result of an instruction execution, such as arithmetic overflow, division by zero, attempt to execute an illegal machine instruction, and reference outside a user's allowed memory space.

>Timer Interrupt - Generated by a timer within the processor, This allows the operating system to perform certain functions on a regular basis.

>I/O Interrupt - Generated by an I/O controller, to signal normal completion of an operation or to signal a variety of error conditions.

>Hardware Failure Interrupt - Generated by a failure, such as power failure or memory parity error.

An operating system (OS) can handle multiple interrupts in a couple different ways. First is the disabled interrupt in which all interrupts are ignored. This works sort of like a queue where new interrupts are pushed to the back of the line to be processed after interrupts have been re-enabled again. In this scheme, if a hard disk I/O interrupt occurred because the device needed to store some value to its memory and a mathematical operation from a program interrupt occurred, the first interrupt would take precedence and immediately disables all successive interrupts. Then, once the interrupt routine is completed, interrupts will be re-enabled and the program interrupt and any additional interrupts gained during the last interrupt-handler cycle will take place.

The second way in which an operating system can handle multiple interrupts is to create a priority managed system in which high priority interrupts are executed before the low priority ones. In this approach if we had some particular interrupt that needed to be processed immediately we may assign it a very high priority so that is take precedence over some data that can wait for processing with little to no effect.

How an interrupt is handled is a very important decision. If an interrupt is handled incorrectly the system could miss an important system call and become unstable, data could be lost, or operations could not complete correctly. Using the appropriate interrupt for the appropriate situation is key to avoiding these issues and more unexpected behaviors within your OS.
